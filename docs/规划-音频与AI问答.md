## 二、F1 音频能力

### 2.1 先确认是"哪一种放音乐"（难度差很多）

| 理解 | 内容 | 难度 | 粗估 |
| --- | --- | --- | --- |
| A. 播放器 | 应用里放背景音乐 / 自己的歌，有播放列表、切歌、后台播放 | ★☆☆☆☆ | 0.5–2 天 |
| B. 卡片语音笔记 | 给知识卡片录 / 挂自己念的批注 | ★★☆☆☆ | 3–7 天（含 PC↔手机同步） |
| C. TTS 朗读 | 把卡片内容或 AI 答案读出来（"听文献"） | ★★☆☆☆ | 1–3 天（用云 TTS） |

> 待用户确认是 A / B / C 中的哪一种（可以多选）。

### 2.2 技术路径（贴合现有栈）

本项目现有形态是 **FastAPI + SQLite + Web UI + pywebview 桌面壳**，手机端已能通过局域网浏览器访问
（见 `手机访问说明.txt`：`http://<电脑IP>:8011`）。因此：

| 端 | 播放方式 | 说明 |
| --- | --- | --- |
| PC（pywebview 桌面窗口） | HTML5 `<audio>` | 无额外依赖，直接可用 |
| 手机（浏览器访问） | HTML5 `<audio>` + **PWA Media Session** | 后台播放 / 锁屏控制需要 PWA（`manifest` + Service Worker）或将来做原生壳 |
| 将来若做原生 App | `just_audio` + `audio_service`（Flutter）等 | 只有确定要走原生路线时再引入 |

**必须一项项实机测的琐事**（不是难点，但躲不掉）：音频焦点（来电 / 其它 App 播放时暂停）、
蓝牙切换、锁屏控制、后台播放权限（iOS 尤其严格）。

**版权边界（硬约束）**：**不内置版权音乐**，只播放**本地 / 用户自有**的音频文件。

## 三、F2 内嵌 AI 问答与检索

### 3.1 为什么这个项目做化学 RAG 有别人没有的那一半

本项目已经具备别人做化学 RAG 做不出来的能力：

- **RDKit 子结构 / 相似度检索**（"含这个骨架的化合物""这个底物范围里有没有缺电子芳环"——
  向量检索**答不了**，只有结构检索能答）；
- **已结构化的卡片**：反应物 / 产物 / 试剂 / 溶剂 / 温度 / 时间 / 产率 / 影响因素 / 底物范围 / 机理；
- **图证据链**：每张卡片都能回到原始反应式图与原文。

所以正确的架构是：

> **结构检索是一等公民；向量检索只补语义；AI 只负责"把检索到的卡片说成人话 + 引用卡片"，
> 不允许它凭记忆回答化学。**

### 3.2 四层拆解与难度

| 层 | 内容 | 难度 | 粗估 |
| --- | --- | --- | --- |
| 检索 | 混合检索：关键词（已有 jieba+倒排）+ **子结构/相似度**（已有 RDKit）+ 向量（新增） | ★★★☆☆ | 1–2 周 |
| 生成 | LLM 把检索结果讲成人话，**强制带引用** | ★★☆☆☆ | 3–5 天 |
| 部署 | PC 本地模型（Ollama / llama.cpp + Qwen 系 GGUF） | ★★★☆☆ | 3–5 天集成 |
| 部署 | 手机端跑本地大模型 | ★★★★★ | **不建议**（月级且体验差） |
| 门禁 | 评测集 + 防幻觉规则 + "无证据就拒答" | ★★★★☆ | 1–2 周，且**要长期维护** |

**手机端策略**：手机只读（既定）→ 走现有 Web UI，检索在 PC 侧完成，
生成走**云 API 或 PC 上的本地模型**，手机不跑大模型。

### 3.3 现状盘点（已有 / 缺什么）

| 已具备 | 位置 |
| --- | --- |
| 关键词检索（中文分词 + 倒排） | 现有检索实现（jieba） |
| **子结构 / 相似度检索**（RDKit） | 现有检索实现 |
| 结构化卡片 + 反应式图 | `data/`（SQLite）+ `images/` |
| 大模型调用与多provider 路由 | `app/llm.py` + `models.local.json` |
| 手机访问（局域网 Web） | `手机访问说明.txt` |

| 缺 | 说明 |
| --- | --- |
| 向量检索与混合排序 | 建议 `sqlite-vec` 或 LanceDB 跟着 SQLite 走，少引一个独立服务；嵌入模型选中文友好的（如 bge-m3 系） |
| 引用（citation）机制 | 答案必须带卡片 id + 原图，前端可点回 |
| 拒答门禁 | 检索不到证据就不答，而不是让模型编 |
| **评测集** | 决定这个功能到底可不可信（见第四节） |
| 语音提问 | 与既有"语音检索"目标合并（ASR：faster-whisper 本地或云） |

### 3.4 门禁规则（不可协商）

1. **无证据不答**：检索命中为空或分数过低 → 明确回"库里没有相关证据"，不生成化学结论。
2. **强制引用**：每条结论都要挂卡片 id；**没有引用的答案一律视为失败**。
3. **AI 不得改数据**：不能编辑卡片、不能改结构、不能"顺手"修正反应式（改结构仍走 chem-ocsr 的编辑回路）。
4. **答案可回溯**：能点回卡片与原反应式图（与 chem-ocsr 的证据链同一思路）。
5. **区分"库里有"与"文献里有"**：只依据库内卡片回答，不外推到模型记忆。

## 四、评测集：决定 F2 可不可信的地方

**三类题**（每题都要带"标准答案 + 允许引用的卡片 id"）：

| 题型 | 例子 | 考什么 |
| --- | --- | --- |
| 事实题 | "某反应的最佳碱是什么？" | 能不能从卡片里准确取数并引用 |
| 结构题 | "库里哪些反应用了芳基溴化物？" | 子结构检索是否被优先使用 |
| **拒绝题** | "库里有没有做过这个反应？"（其实没有） | **能不能拒答**，而不是编一个像样的答案 |

**三个指标**：引用正确率、答案正确率、**拒绝题的正确拒答率**（最后一项是红线）。

**起步规模**：从现有卡片里抽 **30–50 题**即可开始；每次改检索/提示词都回归一遍。

> 这一节是"先建评测、再谈效果"：没有评测集时，"AI 答得挺好"只是错觉。

## 五、归属与阶段

- **归属**：F1、F2 都属本项目（知识底座 + 应用）；**chem-ocsr 不参与**（它只做图片→SMILES→可编辑结构式）。
- **与既有目标合并**：语音检索 / 片段检索 / 关键词检索本来就写在最终目标里，F2 是把它们串成一个问答入口。
- **建议实施顺序**：
  1. 检索层先做好（**不接 AI 也能用**）：关键词 + 子结构 + 向量，混合排序；
  2. 再加"生成 + 强制引用"；
  3. 然后建评测集与门禁；
  4. 最后才是语音提问与 TTS 朗读（F1 的 C 类）。
- **F1 与 F2 解耦**：F1（播放器）可以独立先做，不依赖 F2。

## 七、风险

| 风险 | 级别 | 缓解 |
| --- | --- | --- |
| **AI 幻觉被当真**（化学答案错了肉眼看不出来） | 高 | 强制引用 + 无证据拒答 + 拒绝题评测；结论只来自卡片 |
| 版权音乐 | 中 | 只播本地/自有音频，不内置内容 |
| 手机端后台播放受限（iOS 尤其） | 中 | 做 PWA 或降低预期（前台播放） |
| 依赖膨胀（向量库 / 嵌入模型 / 本地模型） | 中 | 向量库随 SQLite（sqlite-vec）；本地模型可选、不作为必需路径 |
| 评测集维护成本 | 中 | 起步只做 30–50 题，随功能增量扩 |
| 范围蔓延（跑到 chem-ocsr 里做音乐/问答） | 中 | 本文档与 ADR-035/036 明确归属 |
